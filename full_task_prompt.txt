## 1. Data traps to verify and handle (each is a known risk in the pack)
- **Timezones.** created_at and first_response_at are IST. Legacy resolved_at (source_system=legacy_fd) was rebuilt from a UTC event log. Test for a ~5.5h offset: compare resolved_at minus created_at for legacy vs helpdesk rows, and count resolved_at < created_at or < first_response_at. If confirmed, correct legacy resolved_at by +5:30, keep the raw value, and add a flag. Note the helpdesk API exports UTC, so confirm the CSV isn't mixed.
- **Legacy currency.** The legacy tool stored money in a "native unit". Compare the refund_amount_inr distribution for legacy vs helpdesk (for example a 100x factor) and check it against products.retail_price_inr. Normalise only if the evidence is clear, and document it.
- **Duplicates / re-imports.** Pre-14-Sep-2025 tickets may appear under both sources, with odd IDs. Detect duplicates on ticket_id, and on a content key (customer_id, created_at, channel, product_sku, normalised customer_message). Flag them, exclude duplicates from headline metrics using a documented keep-rule, and show counts before and after. Duplicated refunds must not be double-counted.
- **CSAT.** Blank means no response. Legacy 0 means no response. Convert both to NaN and never average zeros. Auto-closed tickets are surveyed, so check whether CSAT exists on status=closed rows.
- **Status.** Attendance/closure = status in (resolved, closed). Exclude open and pending from closure counts. Report resolved and auto-closed separately.
- **Category.** The `category` column is an intake-bot tag, not ground truth. Use it only as a weak hint and as a baseline to beat.
- **Joins.** order_id is often blank. Fall back to customer_id + product_sku, and pick the latest order on or before created_at. Report the join rate and the ambiguous-match rate.
- **Roster.** One row per assignment. Resolve an agent's team, tier, site and shift effective at resolved_at (from_date <= date <= to_date). Join on agent_id, never on name. Flag agents missing from the roster or with overlapping roster rows.
- **Refund + replacement.** The policy forbids both for the same order. Find tickets and orders with a refund and replacement_issued=Y (also across duplicate tickets). Also check refund_reason_code against message text and notes (for example GW-OTHER used as a catch-all, or DOA-REPL on tickets that are not DOA). Report the mismatch rate.
- **Lot codes.** Join orders.lot_code and test whether specific complaint categories (battery, connectivity, damage) concentrate in specific lots or SKUs beyond the base rate.
- **Language.** Check whether messages include Hinglish, transliterated text, or voice IVR transcripts with transcription noise. Handle these in tokenisation and prompting.
- **Date edges.** The window ends 30 Jun 2026. Weeks are Monday-start in IST. Flag partial first and last weeks. Repeat-contact rates need right-censoring: a ticket resolved less than 30 days before the data end can't be judged, so exclude it from the rate denominator and say so.

## 2. Preprocessing (src/preprocessing.py)
Produce outputs/tickets_clean.parquet or csv with parsed timestamps, week_start, corrected fields and the enrichments below. All calculations are deterministic and unit-tested:
- sla_target_min by channel (chat 15, voice 120, social 240, email 480). Compute first_response_minutes, sla_breach (first response later than target). A missing first response gets its own flag and is not treated as a breach unless the policy implies it.
- sla_credit_inr = 350 for each breach on tickets that are resolved or closed.
- contact_cost_inr by channel (chat 210, email 260, voice 520, social 240). Also report the blended 290 for comparison. Use channel costs as primary.
- transfer_cost_inr = transfers * 305.
- replacement_cost_inr = products.unit_cost_inr + 340 when replacement_issued=Y.
- handle_minutes = resolved_at - first_response_at, using corrected timestamps.
- Mask PII in any text shown in the UI or sent to the LLM (phones, emails, long digit strings). Never show customer names.

## 3. Hybrid retrieval layer (src/retrieval.py)
Build one reusable hybrid search over customer_message (optionally combined with the product name):
- BM25 via rank_bm25 with simple tokenisation (lowercase, strip punctuation, light stopwords, keep model-number tokens).
- Dense vectors from an Ollama embedding model. Cache embeddings to outputs/embeddings.npy keyed by a hash of the text, and embed in batches. Use numpy cosine similarity, with no external vector store.
- Reciprocal Rank Fusion: score = sum(1 / (k + rank_i)), k=60 configurable. Return the fused rank plus each component's rank and score so results are explainable in the UI.
- Include a small function to evaluate BM25-only vs vector-only vs RRF on the labelled set (recall@k of same-category neighbours).
Use it for exactly these four things and nothing else:
1. **Few-shot retrieval for classification.** For each ticket, retrieve the top-k (default 4) labelled examples from the dev pool (never from the locked test set) and insert them in the prompt.
2. **Repeat-contact evidence.** Text-similarity signal between a ticket and a later ticket from the same customer (see section 5).
3. **Representative complaints.** For each category and week, pick examples by RRF against the category's centroid or top terms. Deterministic, PII-masked.
4. **"Ask the tickets" page.** A search box where a CX manager types a question. Retrieve the top 10 tickets with hybrid search, then ask Gemma to answer using only those retrieved messages. Show the sources and the BM25, vector and RRF ranks.

## 5. Repeat contacts (src/repeat_contacts.py)
Transparent, rule-based, documented in the module docstring and on the page:
- For each resolved or closed ticket A, look at later tickets B from the same customer_id created within 30 days after A's resolved_at (use corrected timestamps).
- Score B as a repeat of A from independent evidence: same order_id, or same product_sku (only where order_id is missing), same classified category, hybrid text-similarity above a threshold, and phrases like "already told / again / still not fixed / second time" (a small regex list). Require a minimum evidence score, and keep a `match_reason` column. Report a strict definition and a loose definition, and show the sensitivity of the rate to both.
- Same customer alone is never a repeat.
- Right-censor the last 30 days of data. Cost each repeat at the channel cost of the repeat ticket.
- Test the "I already told your colleague" claim from the data. Compare transfers>0 tickets against the rest: their repeat rate, their rate of tickets whose message contains those phrases, and the share that are chat. Also look at whether a repeat is more likely after a first ticket that was transferred, auto-closed, or resolved fast. Report the finding either way, with counts. Do not assume it is true.
- Save outputs/repeat_contacts.csv (pairs, evidence, reason).
- Validation of the matcher: sample 50 pairs, generate a labelling sheet (same issue: Y/N), and report precision on the human labels.
